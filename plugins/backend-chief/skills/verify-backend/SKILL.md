# バックエンド検証

## 入力

変更内容、既存の設定・設計記録、既存CIと検証コマンド、利用できるテスト環境。

## 手順

1. [テスト戦略](../../references/testing.md)でリスクと検証種別を対応させる。既存の依存定義・接続設定・検証手順から採用DBと実行対象を確認する。
2. format、静的解析、依存方向、unit、race、build、契約と生成差分を必要なmoduleで実行する。存在しないコマンドを実行済みとしない。
3. 実DBのintegrationは専用環境を確認して実行する。PostgreSQL・MySQL・NoSQLの未採用品は対象外。接続不能をskipで隠さない。
4. Domainの変更は生成/再構成・等価性・参照漏出・集約の保存復元を対象に応じて確認する。変更されたHTTP/worker経路を通し、認可、失敗、ログ、再送や並行性など関係する負例も確認する。
5. CIがある案件では該当revisionの結果を確認し、ローカル結果と分ける。失敗した場合は原因を絞って修正範囲を判断する。

## 出力

コマンド、版、対象、結果、証拠、未確認と理由。 [共通形式](../../references/output-contracts.md)に従う。

## 情報不足

DBやCIへ接続できなければ独立チェックを済ませ、再実行条件を記す。未確認を合格に言い換えない。

## 完了条件

依頼対象に必要な検証結果が判定され、未検証範囲が明示される。
