# API契約・互換性

## 適用条件

エンドポイント、DTO、HTTPエラー、BFF連携。

## 判断基準

指定Web APIガイドラインの該当節を読み、OpenAPIとエラー対応を先に定義する。Go structをそのまま公開契約にしない。未指定・ゼロ・null、ページング順序、列挙値追加の影響を扱う。最終認可と業務整合性はバックエンド、画面横断の集約と表示変換はBFFとの契約で決める。

## 理由

ビルドが通ってもクライアントの入力・型・再送手順を壊す変更はある。

## 具体例

DBの内部列を応答へ漏らさず、注文DTOを明示する。新しいenum値に既存クライアントが対応できるか確認する。

## 例外・案件判断

既存契約の変更は互換性と利用者影響を記録し段階移行する。RFC例と指定ガイドラインの推奨が異なるとき、黙って置き換えない。

## 検証方法

OpenAPI lint、生成差分、実HTTPの成功/失敗契約、消費側との互換性を確認する。詳細はAPI規約。
