# 業務の理解からモデルを更新する

業務ルールの新設・変更、集約やコンテキストの設計で読む。モデルは実装前に一度完成させる仕様書ではなく、業務の発見をコードへ反映するための共通理解として扱う。

## 具体例から意味を確かめる

1. 利用者、解決したい問題、今回扱う操作を絞る。既存のモデル・仕様・テストと実装の差を確認する。
2. ドメインエキスパートや利用者の説明から、正常な具体例、境界例、成立しない例を集める。例えば「取消可能」だけでなく、出荷直前・出荷後・一部出荷時の注文をどう扱うかを確認する。未提示のルールは仮説として分ける。
3. 具体例から用語、関連、多重度、状態遷移、ルールと制約を表す。日本語とコード上の英語名の対応、同じ言葉の意味が変わる範囲も決める。ユビキタス言語は表記統一だけでなく、会話・モデル・コードで意味を共有すること。
4. ルールを守る所有者と集約境界を仮置きし、具体例で破れないか確かめる。未決事項には影響と次の確認先を残し、独立に進められる部分を実装する。
5. 実装・テスト・業務確認で発見があれば、モデルの意味を確認してコードと回帰テストへ反映する。実装の都合だけでモデルを黙って変えない。既存のモデル記録も同じ変更で更新する。

図は認識を揃えるために選ぶ。システム関連図は範囲と外部関係、ユースケース図やユーザーストーリーは利用者の操作、ドメインモデル図は概念・ルール・集約、オブジェクト図は具体例を表す。状態遷移や処理順が複雑なら状態遷移図・シーケンス図を使う。全種類の図、特定ツール、別の用語台帳を必須にしない。既存の管理場所を使い、小変更は短い記述でよい。

## 集約の境界を決める

集約は一緒に守る不変条件を持つ単位で、集約ルートが子の変更を含めて管理する。テーブルの親子関係、APIのリソース名、画面に同時表示されることだけで境界を決めない。

| 判断材料 | 確認すること |
|---|---|
| 整合性 | 必ず同時に成立すべきルールか、一時的な不一致を許すか。その不一致の損失は何か |
| 変更のまとまり | どの操作がどの状態を一緒に変更するか。ほぼ常に同時変更する集約は境界を見直せないか |
| データ量 | 子の件数と増加率、取得・再構成の負担が妥当か |
| 競合 | 無関係な変更まで同じロックやversionで競合させないか |
| 実装と検証 | 一つの集約で守る簡潔さと、分割後の調整・失敗処理の費用は釣り合うか |

例えば、部員が減ると部の承認状態も変わるなら、部員だけの削除で条件を迂回させない。一方、学校全体を集約にすると別々の部の変更まで競合する可能性がある。整合性だけでなく件数・競合を比較し、実装後も境界を見直す。

集約内部を必要な原子単位で確定することと、1 Txに必ず1集約だけ含めることは別。複数集約を同じDBのTxに含める場合は即時整合性の必要性、ロック範囲、失敗時の扱いを説明する。跨DBや外部サービスの保証は[整合性](../principles/consistency.md)で別に設計する。

## コンテキストとコードの対応

コンテキストは言葉とモデルが適用される範囲、集約は整合性の単位、Go packageは可視性・依存を制御する単位。一つのコンテキストに複数集約があってよい。コンテキストごとのプロセスやDB分割は必須ではない。

販売の商品と配送の商品で意味が異なるなら、同じ名前でも万能な共通型へ統合しない。外部の表現は公開契約で受け取り、自分のコンテキストの意味へ変換する。別コンテキストの内部型・テーブルを共有して境界を迂回しない。

同じコンテキストでも、別集約との保持する関連はID参照を基本とする。判断のために他集約を一時的に引数へ渡すことは可能だが、その内部を直接変更する抜け道にしない。共有値型は意味の所有者の近くに置き、特定の所有者がないものだけ共有packageを検討する。

Goでは非公開フィールドも同じpackageのコードから操作できる。集約ごとのpackage分割は保護を強める一案だが、相互参照による循環や公開APIの増加と比較する。既存配置を一律に変えず、packageで保証する境界と規約・レビューで守る境界を明記する。循環回避のために業務型を何でもsharedへ移さない。
