# 命名・コメント

対象は識別子と説明の変更。名前はコードを読む範囲と業務の語彙から決める。

| 観点 | 採用する判断と理由 | 条件・例外 | 確認方法 |
|---|---|---|---|
| 名前の長さ | 局所のindexやreceiverは短く、離れた場所で使う名前は意味を明示する | 全変数を一文字にしない。業務用語の曖昧な略語を作らない | 宣言と利用箇所を一緒に読んで役割が分かるか |
| 型との重複 | `usersMap`より`usersByID`など目的を表す。package名との重複を避ける | 型の区別自体が契約上の意味を持つ場合は残す | 名前が格納形式だけを説明していないか |
| 一貫性 | 同じ概念には同じ単語・receiver名を使う | 異なるBounded Contextの同名概念は無理に共通化しない | 関連する呼出しと業務用語を検索する |
| MixedCaps | `userID`、`HTTPClient`。snake_caseをGo識別子へ持ち込まない | JSON/DBの名前、既存公開API、生成物は契約に従う | Go名とwire名を分けて差分確認 |
| getter | 通常は`Owner()`、変更操作は意図に沿う動詞にする | `Get`に取得・I/Oの意味があるAPIを機械的に改名しない。Domainに無条件setterを作らない | 名前と副作用・検証の有無が一致するか |
| interface名 | 1つの振る舞いなら自然な`-er`名。`I`接頭辞や`Interface`接尾辞を避ける | Repository等の業務契約を命名だけのために1メソッドずつ分解しない | 役割とメソッド集合が一致するか |
| 名前とコメント | 名前で表せる意味を先に改善し、コメントで契約や理由を補う | 不明瞭な略称を大量のコメントで補わない | コメントを外すと本体が読めなくなる原因を確認 |
| doc comment | 公開宣言と自明でない非公開宣言を説明する。nil/ゼロ値、所有権、副作用、エラー契約、並行安全性を必要に応じ記す | 自明な内部処理の逐語訳は追加しない。日本語を許容し、識別子と説明の対応を保つ | 利用者が本体を読まず安全に呼べるか |
| コメント量 | 意図、制約、意外な挙動を書く。コード変更時に更新する | 行数やコメント率は目標にしない。古い処理のコメントアウトを残さない | 実装・テストと説明の食い違いを探す |
| Go doc構文 | 見出し・リンク・リストはGo doc構文を使う。非推奨には移行先と理由を記す | 一般Markdownの全構文が使えると仮定しない。`//go:`ディレクティブを整形で壊さない | `go doc`で対象の表示を確認 |
| Example | 利用方法の理解に有用な公開APIに実行可能なExampleを置く | 全getterへの追加は不要。`Output:`等がないExampleはコンパイル確認のみで実行されない | 出力付きExampleを`go test`で実行し、決定的な出力を確認 |

互換性のある公開名は記法だけで変更せず、内部名と新設APIから揃える。型を公開したくない理由と、Domainのカプセル化は[interface・パッケージ](interfaces-and-packages.md)と[Domain実装](../domain-implementation.md)で判断する。
