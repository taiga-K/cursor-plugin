# レビュー観点

対象差分に関係する行を選び、入力・状態・停止位置から実害を評価する。全項目を形式的な承認ゲートにしない。

| 観点 | 確認する問い |
|---|---|
| Goの書き方 | [go-coding](../skills/go-coding/SKILL.md)の関連標準に沿うか。採用版・公開互換性を守り、不具合と記法上の差を区別したか |
| 業務 | 具体例とモデルのルールがコード・テストに対応するか。集約内の不変条件を原子的に守るか。複数集約のTxは意図的か |
| Domain | Entityの同一性とVOの等価性・不変性が正しいか。子や参照の漏出からルールを迂回できないか |
| 生成・復元 | 新規生成と再構成が分かれ、ID・状態・業務日時を保つか。破損・旧版データとゼロ値を扱うか |
| Repository | 集約単位の契約か。業務判断がAdapterへ漏れていないか。部分更新時もルートの条件・versionを守るか |
| 責務配置 | RepositoryとQuery等のportの所有先は妥当か。Service/Factoryの肥大化やユースケース呼合いがないか |
| 参照 | Query DTOと更新用集約を混同せず、必要な認可・整合性・検索効率を保つか |
| 依存 | Domain/ApplicationがGin・DB型・platform実装をimportしていないか |
| 入出力 | HTTP固有型とApplication DTOを区別するか。未指定と0/false、型変換、金額精度、日時の意味は保たれるか |
| 認可 | tenantや主体が入力任せでないか。対象単位の最終認可があるか |
| 取引 | callbackの全操作が同じTxか。commit失敗と結果不明を扱うか |
| 競合 | 事前SELECTだけで一意性を保証していないか。更新件数0を検知するか |
| 冪等 | keyのscope、payload一致、処理中、期限、応答断を扱うか |
| DB | 実製品の分離レベル・DDL・条件付き操作・型変換を確認したか |
| API | 指定規約、Problem Details、HTTP status、互換性、body省略が整合するか |
| ログ | 必須キー・単位・相関・秘密・重複出力・メッセージコードは適切か |
| 並行処理 | contextを渡し、goroutine・pool・response bodyを回収するか |
| 外部連携 | Domain Eventと外部配送を区別し、rollbackした変更を配信しないか。retryの二重副作用や受領と完了の混同がないか |
| 性能 | 上限・安定順序・索引・N+1・hot key・cache失効に根拠があるか |
| 移行 | 新旧混在、途中停止、再実行、照合、戻せない変更を扱うか |
| 検証 | 実DB未実行を隠していないか。負例が変更前に失敗するか |
| 責務 | プログラム構築からクラウド資源の作成へ勝手に範囲を広げていないか |
