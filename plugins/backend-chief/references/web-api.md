# Web API規約の適用

指定資料は[Future Web API設計ガイドライン](https://future-architect.github.io/arch-guidelines/documents/forWebAPI/web_api_guidelines.html)。確認日2026-09-13。これは全文転載ではなく、実装時の参照索引とGo側の判断をまとめたもの。実装する機能の該当節を読み、条件付き推奨も確認する。ガイドラインを取得できない場合は確認済み範囲と未確認を分ける。

## 指定資料の対応表

| 参照する節 | 採用する規約 | 検証 |
|---|---|---|
| APIバージョニング | 互換性を維持し、必要な破壊的変更はパスのメジャー版と移行期間で扱う | 契約差分、旧consumer |
| HTTPメソッド | 作成はPOST、更新はPUTを基本に部分更新要件ならPATCH。GET bodyは使わない | OpenAPI、実HTTP |
| POSTとPATCHの冪等 | Idempotency-Keyと要求の同一性を照合。同一キーの異なる入力は400 | 並行送信、再送 |
| レスポンスボディ | 一覧はオブジェクトで包む。欠損は原則キー省略、日時はISO 8601 | JSON契約 |
| エラーについて | RFC 9457、application/problem+json、errors配列 | エラーごとの応答 |
| 排他制御 | バージョン番号方式。更新競合409、DELETEではlock_noをクエリで指定 | 同時更新・削除 |
| タイムアウト | 同期APIで独自の処理期限を原則追加せず呼出元のキャンセルを伝播。非同期は最長実行時間を決める | キャンセル、job打切り |

## エラー分類の実装

HTTPへ変換する場所をGin Adapterへ集約する。入力形式は400、認証は401、認可は403、不存在は404、業務上の競合は409、業務条件不成立は422、想定外のシステム異常は500を基本に、原資料のステータス表で判断する。503は一時的な提供不能等の意味に合う場合だけ使う。

返却するtypeは管理した問題種別のURIにし、titleとerrors内のdetailには利用者へ開示できる説明を設定する。errorsは一件でも配列。フィールドの位置情報を返す場合はOpenAPIで表現形式を固定する。クライアントの分岐を自然言語のtitleへ依存させない。業務エラーと診断用の生エラーは分離する。

## Go向けの補足判断

以下は本プラグインの推奨。原資料の引用ではない。

- DTOの必須判定にGoのゼロ値だけを使わない。更新の「未指定」「0」「false」、必要な場合のnullを区別する。omitemptyが正当な0を落とさないかテストする。
- Ginの既定404/405やpanic応答もAPI契約に合わせる。書込済みのレスポンスへエラーJSONを追記しない。
- 204ではbodyを返さない。201や202は永続化や耐久的な受領の成立と対応させる。
- 冪等キーの保存範囲は主体・操作で分け、同一性のcanonicalization、処理中・完了・結果不明、結果再現、保持期限を設計する。キーだけ先に保存して仕事を失わない。
- 一覧のページ方式・キー命名は原資料のクエリパラメータ節を参照し、上限、安定順序、全件数の必要性を契約化する。SQLのoffsetをNoSQLへ無条件に持ち込まない。
- 同期Handlerに一律のcontext.WithTimeoutやtimeout middlewareを足す標準にはしない。既存deadlineは下流へ渡す。接続確立・ヘッダー読取・終了処理の上限と業務の処理期限は区別し、追加の上限が必要なら目的とガイドラインとの差をADRに残す。

## 適用範囲・差異

Gateway、CORSの機能配置、ネットワーク認証、レート制御など基盤側の章は[インフラ契約](infrastructure-handoff.md)へ渡す。配置先が別でも、その機能が実在すると推測しない。

ガイドライン内の例、本文、HTTP標準に不一致がある場合は根拠を併記する。例えば廃止ヘッダーやHTTP条件付き要求を実装する際は、現在の該当RFCも確認し、古い例をそのまま生成しない。指定標準からの逸脱が必要なら適用範囲と理由を利用者へ提示し、未合意を準拠扱いしない。
