# DomainをGoの型と振る舞いへ落とす

Entity・Value Object・Repository・Domain Serviceの設計、実装、レビューで読む。固定のpackageや型名を生成する手順ではない。業務の意味は[モデリング](domain-modeling.md)から確定し、次の判断を適用する。

## 責務の所有者

| 要素 | 所有するもの | 避けるもの |
|---|---|---|
| Entity・集約ルート | 識別子による同一性、状態遷移、子を含む不変条件 | 汎用setter、子の直接変更、DBアクセス |
| Value Object | 値による等価性、値固有のルール、不変な値 | ポインタ同一性による判定、外部からの内部変更 |
| Domain Service | Entity/VOへ自然に置けない集合や複数対象の業務判断 | 業務処理を何でも集めるXxxService |
| Factory | 複雑な生成、生成に必要な他集約の参照・判断 | 単純な生成にも一律追加、保存・通知まで暗黙に実行 |
| Repository契約 | 集約を取得・保存する意味と単位 | テーブル別の子Repository、業務判断をAdapterへ移すメソッド |
| Application | 操作の調整、主体と対象の認可、Tx境界、必要な入出力 | Domainのルールを入口ごとに再実装、HTTPやDB実装への依存 |

まずEntity/VOの振る舞いを検討する。例えば予約集合に対する重複判定は個々の予約自身に置くと不自然なので、責務を表す名前のDomain Serviceを候補にする。Domain所有のRepository契約を使って判断する方式と、Applicationで情報を取得して純粋なDomainの判断へ渡す方式を比較できる。いずれも事前確認だけでは並行予約を防げないため、保存時の制約・条件付き操作も設計する。

生成だけが複雑ならFactoryを候補とし、生成後の保存はApplicationが調整する。Domain Serviceへ保存を含む業務操作を置く場合は、そこで守るルールとTxへの参加を説明する。すべてのServiceに同じ実装形を強制しない。

同じコンテキスト内で公開ユースケースを安易に呼び合って再利用しない。循環がなくてもTxの入れ子、認可の重複、副作用の二重実行、処理経路の肥大化を招く。共通の業務判断はDomainへ、取得・変換等のApplication共通処理は独立した関数や型へ切り出す。コンテキスト間の公開Application契約による連携は別であり、各境界の認可・確定点・失敗を定める。

## 同一性・等価性・所有権

Entityは属性が変わっても同じIDなら同じ対象、同じ属性でも別IDなら別対象として扱う。Entity自体を不変にする設計も可能。IDの形式や全型への独自ID導入は固定せず、取り違えを防ぐ効果から判断する。

VOは意味を構成する値で等価性を定義し、変更は新しい値を返して表す。単に不変条件を満たす可変structではない。通貨を含む金額、期間、メールアドレスなど、独立したルール・単位・取り違え防止に意味があるときに使う。全プリミティブを無条件にVOへ変えない。

Goのstructを値渡ししても、内部にslice・map・pointerがあれば参照先を共有し得る。constructorの引数とgetterの返却値から内部を書き換えられないか確認し、必要な深さのコピーや不変な表現を選ぶ。sliceの要素がpointerならsliceだけのコピーでは足りない。集約の子を返す場合も、呼出し側がルートを迂回して変更できない表現にする。

`==`が使えるかと業務上の等価性が一致するかは別に確認する。slice/mapを含む型や、正規化・順序の意味を持つ値は必要な比較を定義する。正規化も業務規則から決め、推測で値を変えない。[Go仕様](https://go.dev/ref/spec#Representation_of_values) / [比較規則](https://go.dev/ref/spec#Comparison_operators)

## 新規生成・状態変更・再構成

| 経路 | 契約 |
|---|---|
| 新規生成 | 初期状態、作成時だけの条件、ID・業務日時を決める |
| 状態変更 | 現在状態から許された操作か検証し、失敗時も不正な途中状態を残さない |
| 再構成 | 保存済みID・状態・履歴を保ち、新規作成の初期化・採番・通知・イベント発生を繰り返さない |

例えば完了済みタスクのロードに「作成時は未完了」というルールを適用しない。新規生成と再構成で共用できるのは、常に成立する値や構造の条件であり、作成時だけの条件とは分ける。

再構成は専用関数等で意図を表し、通常のユースケースから任意状態を作る抜け道にしない。プロダクトコードでは永続化Adapter等の復元経路から利用し、テストから使う場合も有効な状態を準備する。Goの公開型のゼロ値をconstructorだけで防げるとは考えず、意味のあるゼロ値にするか、公開操作・境界で無効な状態を拒否する。型、package境界、規約、必要な検査が保証する範囲を分ける。

復元時に検証するかは一律に決めず、常に成立すべき不変条件と破損データの扱いを明示することを求める。検証を省略する経路はデータを信頼できる条件と保証箇所を説明する。ルール変更前に有効だった値を新ルールで一律拒否せず、旧版の読取互換性、移行、エラー時の扱いを設計する。

業務日時とORMのcreated_at/updated_atは同じ意味とは限らない。業務上の期限・成立時刻をDomainの契約とし、採番や時刻は引数または必要な依存から試験で制御できるようにする。すべての案件にClockやIDGeneratorのinterfaceを追加しない。

## 集約単位のRepository

更新用Repositoryは集約ルートを通して整合した状態を取得・保存する。子の状態が必要な集約を部分ロードして完全な集約と偽らず、子専用のRepositoryでルートの条件を迂回しない。検索用の一部項目だけが必要なら[Query Service](architecture.md)を比較する。存在確認、件数取得、削除対象のID指定は契約の意味に合えば使える。

取消可否などの業務判断をRepository実装へ置かない。Adapterはマッピング・永続化・競合検出を担う。集約単位の保存は全カラムを必ず書く命令ではなく、変更列だけのSQLやNoSQLの条件付き操作も選べる。その場合も、Domainの判断とDB条件の対応、子の変更とルートのversion、影響件数を確認する。

楽観ロックは、読み込んだ状態に対応するversionを取得し、期待値として保存時に照合する。Domainに意味のあるversionを保持する方式と、読み取りsnapshotに付帯させる方式などを比較する。DBやORMの型を内側へ漏らさず、保存後に再利用するなら新しいversionの取得方法を決める。Tx rollbackはメモリ上のEntityを元に戻さないため、再試行では新たにロードして操作をやり直す。

Repositoryの契約はDB製品を隠しても、その製品にない原子性を保証しない。外部サービスの操作をportで公開するときも、DBと同じrollbackが効くように見せない。[DB選択](database-selection.md) / [整合性](../principles/consistency.md)

## イベントを選ぶ場合

Domain Eventは業務上起きたことを表す。同期処理でも使用でき、採用だけで非同期配送やキューを要求しない。複数集約の処理はApplicationの調整、Domain Service、Domain Eventを、理解・実装・検証の費用とルールを守る確実さから比較する。

イベントを使うなら、生成する時点、処理がTx内かcommit後か、失敗時に何が確定するかを決める。外部へ公開するイベントは配送用の契約として必要項目・互換性を設計し、Domainの内部structをそのまま公開しない。外部配送が必要なら業務更新とoutboxを同じ原子単位に記録し、rollbackされた変更を確定した出来事として配信しない。配送・再送・重複排除は[外部連携](../principles/reliability.md)に従う。
