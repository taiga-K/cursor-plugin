# 例題と評価基準

これはワークフローの経路と判断を人が評価するためのケース集。validate-contentはリンクの到達性を確認するだけで、自然言語の判断を実行するテストではない。新しいエージェントで試す場合は「依頼と材料」だけを渡し、下記の評価基準は渡さない。特定モデルや並列実行は必須にしない。

## 1. 新規画面

依頼と材料：新規Next.jsアプリで注文履歴を作る。注文APIはidとlabelを返す。FSD・Astryxを採用する。初回読み込み・空・失敗がある。

評価：新規導入→調査→設計→setup-frontend→Astryx確認→実装（story同時）→検証（CI URL）→レビュー。FSDの予約名衝突、所有先、受入条件を扱う。Astryxの未確認propsを発明しない。

## 2. 既存バグ（TDD）

依頼と材料：検索欄を変更すると、新しい結果の後から古い検索結果が表示される。ネットワーク上、古いリクエストほど遅い。画面は既存の独自構成。

評価：バグ修正→調査で競合を再現→**失敗する回帰テストを先に追加し意図した理由で落とす（Red）**→最小修正（Green）→必要なら整理（Refactor）→検証→レビュー。最新要求に対応する結果だけを反映する。既存全体をFSDへ移行しない。失敗テストが非現実的なら理由と代替回帰を明示する。

## 3. FSD違反のレビュー

依頼と材料：features/reorderがfeatures/cancel-orderの内部ファイルをimportした差分をレビューしてほしい。上位の注文ページが両者を表示している。

評価：レビュー手順で調査→レビュー→必要な検証。cross-importと内部API参照の根拠・影響を示し、上位での合成を提案する。修正は依頼されていない。

## 4. Astryx移行

依頼と材料：既存のresetと独自テーマがある注文画面をAstryxへ移す。ダイアログの見た目とキーボード操作を維持する。

評価：段階移行→調査→移行設計→（必要ならsetup-frontend）→CSS基盤・テーマ確認→一部品→一画面→検証・レビュー。採用版を確認し、旧CSSの撤去条件と戻し方を示す。jsdomの成功だけで実部品の操作を保証しない。

## 5. BFFの部分失敗

依頼と材料：Next.js内で注文とおすすめを集約する。注文は必須、おすすめはなくても画面を使える。おすすめのタイムアウトで画面全体が失敗する。

評価：バグ修正または機能追加→調査→BFFの設計（Result / degraded）→失敗テスト→実装→検証→レビュー。失敗を空配列に隠さず注文を保持する。必須失敗、不正応答、空の成功も区別する。サービスの業務ルールをBFFへ移さない。

## 6. Astryx部品の選定

依頼と材料：注文履歴の一覧に「状態で絞り込む」操作を追加する。状態は5種類。既存画面はAstryx採用済みで、別画面の絞り込みに既にある部品が使われている。

評価：UI部品追加→調査で既存の絞り込み部品を確認→選定手順を実行する。要件を「一覧から一つ選ぶ、件数5、キーボード操作」と書き、MCP `search` を役割・一般名・状況の3通り以上で実行し、候補を `get` で読んで比較表を作る。一般名を部品名として書いたら不合格。役割の一致と既存との一貫性で決め、落とした候補の理由を残す。記憶から部品名や props を書かない。選んだ部品を採用版の CLI か型定義で確定し、差分を記録する。story を同時に追加する。

## 7. 既存案件へ検証基盤を導入

依頼と材料：Next.js App Routerの既存アプリ。Jest が一部ある。CI は無い。FSD へ寄せたいが全面移行はしない。検証基盤だけ先に入れたい。

評価：setup-frontend→既存 Jest を置換せず共存条件を設計→templates を差分統合→`pnpm verify` と build→負例で検出確認→GitHub Actions を置き required checks の案内。既存設定を丸ごと上書きしたら不合格。フックで lint を代替したら不合格。

## 8. CI が赤のとき

依頼と材料：PR の frontend-verify が型エラーで落ちている。ローカルでは昨日通っていた。エージェントに「とりあえず緑にして」と依頼する。

評価：verify-frontend→失敗ログと差分を読む→原因を直す。tsconfig / ESLint / テスト期待値を緩めて通したら不合格。`eslint-disable` や `@ts-expect-error` を使うなら理由と期限が必要。報告に CI URL が無いと不合格。

## 9. organisms のテスト種別選択

依頼と材料：注文一覧 organisms を新設する。初期・読み込み・空・エラー・部分成功がある。一覧の行クリックで詳細へ遷移する。認証は既存レイアウト側。

評価：テスト戦略の決定表に従い、状態網羅は Storybook story + play + a11y、遷移を含む画面は必要な E2E スモークに分ける。単体だけで完了したり、全状態を E2E に載せたら不合格。`shared/ui` / organisms に story が無ければ不合格。

## 使い方

スキルや原則を変更したら、各例題について入口の選択表から手順・専門スキル・原則・検証ガイドまで経路と判断を読み直す。実案件で使いにくさや誤った経路を見つけたら、例題を追加して直した理由を残す。この確認は作成者による経路の追跡であり、独立したエージェントに実装させた行動評価とは区別して報告する。
