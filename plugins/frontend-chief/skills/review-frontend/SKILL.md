# フロントエンドレビュー

## 入力

差分または設計、目的、関連契約、既存の検証証拠。

## 手順

1. 変更の意図と影響範囲を読む。周辺の呼出し元・利用画面も確認し、差分だけで断定しない。
2. [レビュー観点](../../references/review-checklist.md)から関係する項目を選ぶ。FSD・UI・状態・BFF・セキュリティの変更に応じた原則本文を読む。
3. 想定する破綻を具体的な入力・操作で検証する。根拠がコードだけならその限界を明示する。
4. [検証原則](../../principles/verification.md)でテストが振る舞いを証明しているか確認する。実装の内部構造の好みは不具合と分ける。
5. 重要度、根拠、影響、修正案を記述する。修正を依頼されていなければコードを変更しない。

## 出力

レビュー形式。指摘ゼロでも見た範囲と未確認を記録する。 [共通形式](../../references/output-contracts.md)を使う。

## 情報不足

仕様が不明な指摘は条件付きの懸念として分ける。推測した仕様を根拠に修正を要求しない。

## 完了条件

各指摘が再現条件または具体的なコード経路を持ち、採否を判断できる。
