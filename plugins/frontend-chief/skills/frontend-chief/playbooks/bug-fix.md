# バグ修正（TDD）

概念：[TDD（Red-Green-Refactor）](../../../references/concepts.md)、[Testing Trophy](../../../references/testing-strategy.md)。

入力：症状、期待値、再現操作、環境。

1. [調査](../../assess-frontend/SKILL.md)で元の操作を再現し、UI→状態→BFF→サービスの経路から原因を絞る。
2. [テスト戦略](../../../references/testing-strategy.md)の決定表で、必要な信頼を得られる最も低い層のテスト種別を選ぶ。
3. **Red**：期待する振る舞いを書いた失敗テスト（または story の `play` / E2E）を追加し、意図した理由で失敗することを確認する。実装の現状から期待値を計算しない。
4. 境界が変わる場合は[設計](../../design-frontend/SKILL.md)、局所修正なら短い原因と方針を記録する（ADR の項目：文脈・決定・結果。独自形式は作らない）。
5. **Green**：[実装](../../implement-frontend/SKILL.md)で原因に対応する最小範囲を修正し、失敗テストを通す。
6. **Refactor**：重複や設計の歪みを直し、テストが緑のままであることを確認する。
7. [検証](../../verify-frontend/SKILL.md)で元の操作・関連回帰と CI を確認し、[レビュー](../../review-frontend/SKILL.md)で副作用を確認する。

失敗テストが現実的に書けない場合（本番限定の状態、再現不能）：理由を明記してから、最も近い実行可能な回帰確認（手動再現手順、ブラウザ操作、ログ断言など）へ切り替える。黙って省略しない。

出力：再現、原因、失敗テスト（または代替回帰と理由）、修正、同条件の結果、CI URL。再現不能なら観測不足を報告する。

完了：修正前は落ちる回帰が存在し、修正後は通り、CI が緑。例外の握り潰しや空配列化だけを解決としない。
