# Astryxとデザインシステム

## 適用条件

UI実装・テーマ変更・既存CSS移行。

## 判断基準

部品は記憶や一般的なReactの知識で選ばず、[選定手順](../references/astryx.md)に従う。要件を役割・情報構造・状態・操作で書き、同梱のAstryx MCPで複数の言い回しから候補を探し、2〜3候補を役割の一致・状態の対応・操作の契約・合成の必要・拡張方法・既存との一貫性で比較して決める。決めた部品のAPIは採用版（CLIか型定義）で確定し、MCPとの差分は採用版を正とする。

推奨：テンプレート → ブロック → 部品 → hook の順に上の層から探す。単なる再exportのための全件ラッパーは作らない。ブランド規約、アクセシビリティ補完、安定した利用側契約に価値があるときにshared/uiへ適応部品を置く。業務固有の合成はそのFSDモジュールが所有する。

## 理由

デザインシステムの部品は役割と操作の契約を持っている。見た目や名前の印象で選ぶと、状態や操作が足りず独自実装・CSS上書き・過剰なラッパーに戻り、更新と一貫性が難しくなる。探索と比較の記録がないと、後から選定理由を検証できない。

## 具体例

「絞り込み条件を一つ選ぶ」なら、MCP `search` で得た候補（2026-09-12時点の例：Selector・MultiSelector・DropdownMenu）を資料の用途と操作契約で比較する。単一選択か複数選択かで Selector と MultiSelector を分け、DropdownMenu は操作の実行であって値の選択ではないと判断する。名前は採用版で再確認し、この例を部品名の出典にしない。既存の検索UIを移す前に、resetとCSSレイヤーの順序、ライト／ダーク、フォーカス、ポップオーバーを確認する。小さい部品で基盤を検証してからページを移す。

## 例外

未提供の部品は合成 → swizzle → 独自実装の順で検討でき、必要な振る舞い、既存部品で足りない理由、探索した検索語、テーマ・操作の契約を明記する。Astryx採用だけでアクセシビリティを保証したと扱わない。MCPが使えない環境ではCLIの `search` と `component --list` で同じ手順を行う。

## 検証方法

設計に「部品選定」の記録（候補、比較、確認元、採用版での差分）があること。採用版の資料、型検査、実ブラウザでのテーマ・操作確認を記録する。取得できないAPIのサンプルを推測で書かない。
