# Astryxの部品選定と採用版確認

Astryxは150以上の部品・hook・テンプレートを持ち、Beta期間中は版ごとに変わる。部品名や props を記憶や一般的なReactの知識から書かない。探索はこのプラグインが同梱するAstryx MCP、採用版の確認はインストール済みの版を情報源にする。[Working with AI](https://astryx.atmeta.com/docs/working-with-ai)、[CLI](https://astryx.atmeta.com/docs/cli)、[移行ガイド](https://astryx.atmeta.com/docs/migration)を採用版と照合する。

## 情報源の使い分け

| 目的 | 情報源 | 備考 |
|---|---|---|
| 何があるかを探す、候補を比較する | MCP `search(query)`、`get(name)` | 自然言語で部品・hook・docs・テンプレートを横断検索。ホスト側の最新資料を返す |
| 選んだ部品のAPIを採用版で確定する | CLI `astryx component <Name>`、`astryx hook <Name>` | インストール済みの版から生成される。導入前なら `npx @astryxdesign/cli` |
| CLIがないとき | `node_modules/@astryxdesign/core` の型定義、`init` が生成したAGENTS.md | 版に一致する |
| 常駐の規約 | `npx @astryxdesign/cli init --features agents` の生成物 | import path、禁止事項（生div、`style={{}}`、マジックナンバー）、CLI早見表 |

MCPの記述と採用版の型が食い違う場合は採用版を正とし、差分を設計に記録する。MCPが使えない環境では CLI `astryx search <query>` と `astryx component --list --detail compact` で同じ手順を行う。検索語に案件固有の機密や顧客情報を含めない。

## 部品選定の手順

UI部品を新設・変更するとき、実装前に次を行い、結果を[設計の「部品選定」](output-contracts.md)に記録する。

### 1. 要件を部品の語彙へ翻訳する

利用者の操作（選ぶ・入力する・確認する・移動する）、表示する情報の構造（一覧・階層・単一値・比較）、必要な状態（読み込み・空・エラー・無効・部分成功）、入力手段（キーボード・タッチ・読み上げ）、画面内の範囲（ページ全体・ブロック・単一部品）を1〜2行ずつ書く。見た目の印象（「ドロップダウンっぽい」）ではなく役割を書く。

### 2. 層を上から見る

ページ全体ならテンプレート（`search` を `template` で絞る、または CLI `astryx template --list`）を先に探し、`template --skeleton` で構造を読む。ブロック単位ならブロックテンプレート、単一の操作なら部品、振る舞いだけなら hook を探す。部品から組み上げる前に、上位の層に既製の答えがないか確認する。

### 3. 複数の言い回しで探索する

MCP `search` を、役割（「複数から一つ選ぶ」）、一般名（「select」「combobox」「menu」）、状況（「フォーム内の絞り込み条件」）の少なくとも3通りで実行する。結果の種別・名前・説明を残し、1回の検索で決めない。上位に出た部品の説明が要件の役割と一致するかを読む。

### 4. 候補を比較する

候補を2〜3に絞り、各候補を `get(name)` で全文を読む。次の観点で比較表を作る。

| 観点 | 見るもの |
|---|---|
| 役割の一致 | 資料が示す用途と、要件の操作・情報構造が同じか。見た目の一致だけで選ばない |
| 状態の対応 | 読み込み・空・エラー・無効・選択済みを props で表現できるか |
| 操作の契約 | キーボード操作、フォーカス管理、閉じる操作、読み上げの扱いが資料に明記されているか |
| 合成の必要 | 単一部品で足りるか、複数部品の合成か。合成なら所有先の[Atomic分類](../principles/atomic.md)を決める |
| 拡張の方法 | ブランド・レイアウトの差を props・トークン・`xstyle` で表現できるか。CSS上書きが要るなら減点 |
| 既存との一貫性 | 同じ役割で既にアプリが使っている部品があるか。あるなら合わせる理由か変える理由を書く |

決め手は役割の一致と操作の契約。複数が同等なら、既存アプリでの使用実績、次に合成の少なさで決める。

### 5. 決定を記録し、採用版で確定する

選定した部品、落とした候補と理由、確認元（MCP、確認日）を設計に記す。次に CLI `astryx component <Name>`（または型定義）で採用版の import path・props・variant を確定し、MCPとの差分があれば記録する。ここで初めてコードを書く。

### 候補がないとき

順に検討する。既存部品の合成 → `astryx swizzle` で部品ソースを複製して拡張 → 独自実装。独自実装には、既存部品で足りない要求、操作契約、トークンの使用、撤去条件を記録する。「見つからなかった」だけで独自実装に進まず、探索した検索語と結果を残す。

## 実装前の確認

1. package.jsonとロックから `@astryxdesign/*` の版、React、Next.js、CSSの構成を確認する。
2. 新規導入なら `npx @astryxdesign/cli init --features agents` を実行し、生成されたAGENTS.mdを読む。依存更新後は `astryx upgrade` で陳腐化を確認する。Cursorのプロジェクトルールは常に読まれるとは限らないため、利用者の環境で `--agent-docs-path ~/.cursor/rules/xds.mdc` へ置く選択肢を提示できる。
3. 部品はサブパスから import する（例：`@astryxdesign/core/Button`）。パッケージ直下からの一括 import を前提にしない。
4. 利用する部品・props・サーバー/クライアント条件・拡張方法・トークンを確認し、参照版と出典を設計に記録する。
5. ブランド指定がある場合、トークンの意味とテーマの拡張方法へ対応付ける。`astryx theme list` から最も近いテーマを起点にする。

## CSS基盤を先に検証

reset、global CSS、CSS Modules、Tailwind等を列挙し、CSSレイヤーとimport順序を調べる。移行ガイドが示す採用版の順序を一か所で宣言し、既存の非レイヤーCSSが上書きしていないかブラウザのcomputed styleで確認する。ビルダーによるimportの扱いも実際の出力で確かめる。

ライト・ダーク、フォーカス、ポップオーバー、ダイアログ、文字サイズを小さな部品で確認してから画面へ進む。ネイティブdialogやPopover APIを使う部品はjsdomだけで判定しない。

## 再利用と独自実装

既存のAstryx部品を先に評価する。ラッパーは、ブランド既定値、安定した利用側契約、必要なアクセシビリティ補完などがある場合に限定する。ラッパーがイベント・ref・disabled・フォーカスを損なわないか確認する。

新しい色やサイズ値は、意味が合うトークンがないことを確認してから扱う。見た目だけの一致で互換性を判断しない。

## 証拠

採用版／探索した検索語と候補／選定理由と落とした理由／確認したAPI／CSSの順序／部品単体と実画面／テーマ別・入力別の操作結果／未確認事項。Astryxを含まないモックやjsdomのテストをAstryxの動作証拠として使わない。
